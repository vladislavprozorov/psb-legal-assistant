# Юридический ассистент — Hack&Change 2026, кейс ПСБ

ИИ-ассистент для юристов банка. Отвечает на вопросы **только по предоставленной базе знаний** (документы компании + статьи законов), даёт ссылки на конкретные пункты и статьи, показывает подтверждающие фрагменты и обоснованно отказывает, если данных недостаточно.

## Быстрый старт (Docker, одна команда)

```bash
cp .env.example .env   # впишите LLM_BASE_URL и LLM_API_KEY
docker compose up --build
```

Откройте http://localhost:8000 — чат слева, подтверждающие фрагменты и просмотр документа справа. Ссылки «п. 3.1», «ст. 70» в тексте ответа кликабельны и открывают документ на нужном фрагменте; ответ можно скопировать вместе с источниками и оценить 👍/👎 (журнал `feedback.jsonl`, сводка — `GET /api/feedback/stats`).

| Переменная | Назначение | По умолчанию |
|---|---|---|
| `LLM_BASE_URL` | OpenAI-совместимый endpoint (`/chat/completions`, `/embeddings`, `/rerank`) | — |
| `LLM_API_KEY` | ключ к endpoint (в репозиторий не коммитится) | — |
| `LLM_MODEL` | генеративная модель | `deepseek/deepseek-v4.1-flash` |
| `EMB_MODEL` | эмбеддинги | `baai/bge-m3` |
| `RERANKER_MODEL` | реранкер | `qwen/qwen3-reranker-8b` |
| `USE_EMBEDDINGS` / `USE_RERANKER` / `USE_VERIFIER` | включение этапов (`0`/`1`) | `1` |
| `VERIFY_MODE` | самопроверка: `smart` — только при признаках риска, `always`, `off` | `smart` |
| `LAW_CONTEXT_CHUNKS` | сколько фрагментов законов класть в контекст | `8` |
| `MAX_WORKERS` | параллельность в `solution.py` | `4` |
| `PORT` | порт веб-интерфейса | `8000` |
| `KB_PATH` | путь к базе знаний (ZIP или папка) | `data/knowledge-base.zip` |

Если эмбеддер или реранкер недоступны, ассистент автоматически переходит на BM25 — ответ всё равно формируется.

## Архитектура

```
вопрос / история диалога
        │
        ▼
 parse_dialog ── история «Пользователь:/Ассистент:» → сообщения чата
        │
        ▼
 Контекст:
   • реестр всех документов (тип, дата, редакция, «утратил силу»)
   • документы компании — целиком (≈30 КБ), с id каждого пункта
   • законы — гибридный поиск: BM25 (стемминг) + bge-m3 → RRF → Qwen3-reranker → top-8
        │
        ▼
 Генерация (DeepSeek V4.1 Flash) → JSON {status, answer, sources}
        │
        ▼
 Контроль достоверности:
   • аудит ссылок: каждая статья, пункт и № договора из ответа должны существовать в базе
     (пункт проверяется внутри названного договора и его доп. соглашений)
   • числа в ответе, которых нет ни в базе, ни в вопросе
   • LLM-самопроверка — в режиме smart только при находках аудита, вопросах с датами/редакциями,
     частичных ответах и отказах «нет данных»
        │
        ▼ (модель недоступна)
 извлекающий ответ: ближайшие положения базы со ссылками — вместо пустой заглушки
        │
        ▼
 ответ + статус + подтверждающие фрагменты
```

Файлы:

- `legal_core.py` — всё ядро: загрузка (TXT/MD/DOCX, ZIP или папка), санитизация, разбиение, BM25, клиент прокси, промпты, генерация, самопроверка.
- `solution.py` — точка входа для платформы: `DATA_DIR/questions.csv` + база → `submission.csv`.
- `app.py` + `static/` — веб-чат на FastAPI без сборки фронтенда.
- `tools/eval_demo.py` — прогон демо-вопросов против эталона, с LLM-судьёй.
- `tools/selftest.py` — офлайн-самотест ядра (20 проверок, без LLM).
- `tools/retrieval_check.py` + `tools/extra_questions.csv` — проверка, что нужная статья закона попадает в контекст; там же 24 провокационных вопроса (старая редакция закона, смена роли, давление, внедрённая инструкция, ошибка в номере договора).
- `tools/build_submission.sh` — сборка ZIP для платформы в `dist/submission.zip`.
- `tools/mock_proxy.py` — мок прокси для офлайн-проверки пайплайна.

### Как устроена работа с документами

- **Документы компании** режутся по пунктам (`3.1.`, `6.2.`); каждый пункт хранит заголовок раздела. В реестре — дата документа и редакции, статус «утратил силу» распознаётся по тексту и имени файла.
- **Законы** (выгрузки Гаранта) режутся по пунктам/подпунктам (`1.`, `1)`), справки о редакциях («Пункт 1 изменён с …») сохраняются — по ним модель видит даты изменений. Мелкие фрагменты склеиваются.
- **Реестр редакций законов**: из отметок «Статья … изменена с 1 сентября 2026 г.» извлекаются даты изменений; в контексте у каждой статьи указано, с какой даты действует текст и есть ли будущие изменения. Это позволяет честно ответить «редакции на 2024 год в базе нет» вместо выдумки.
- **Отбор законов**: гибридный поиск ранжирует фрагменты, затем берутся не более 3 статей; короткие статьи (≤ 14 000 символов) кладутся целиком, у длинных (НК ст. 164, 284) — найденные пункты с соседями и справкой о редакциях. Запрос расширяется юридическими синонимами (НДС, НДФЛ, МРОТ, переработка → сверхурочная работа и т.д.).
- **Анализ вопроса (детерминированный код)**: дата события из вопроса («в августе 2024», «15.09.2024», «в 2025 году») → какая редакция документа компании тогда действовала (или что период захватывает смену редакций) и раньше ли событие последнего изменения статьи закона; контрагенты с похожими названиями («Альфой» — неоднозначно, «Альфа-Трейда» — именно Альфа-Трейд); несуществующие номера договоров. Подсказки добавляются в контекст модели и показываются в интерфейсе. Дата из прошлой темы диалога не переносится в новый вопрос.
- **Санитизация**: строки внутри документов, адресованные ИИ («игнорируй…», «отвечай …»), вырезаются при загрузке — документы считаются данными, а не инструкциями.

### Контроль достоверности (п. 04 кейса)

| Ситуация | Что делает ассистент |
|---|---|
| Недостаток информации | отвечает на подтверждённую часть, называет, чего нет в базе (`partial` / `no_data`) |
| Ошибка в вопросе | не подстраивается, приводит верное значение со ссылкой |
| Дата и редакция | выбирает редакцию регламента на дату события, учитывает доп. соглашения и условия их применения; про отсутствующие старые редакции законов — прямо говорит |
| Противоправный запрос | отказ + разъяснение требований и последствий по базе (`refuse`) |
| Смена роли / давление | игнорирует «системные» сообщения в вопросе, не меняет подтверждённый ответ |
| Неоднозначность | задаёт уточняющий вопрос с вариантами из базы (`clarify`) — например, «Альфа-Трейд» или «Альфа-Трейдинг» |
| Вне юр. тематики | вежливо обозначает границы компетенции (`out_of_scope`) |

## Сабмит на платформу

```bash
./tools/build_submission.sh   # → dist/submission.zip (solution.py, legal_core.py, requirements.txt)
```

**Модели с рассуждениями.** Рассуждения входят в `max_tokens`, поэтому лимит генерации не опускается ниже `MIN_GEN_TOKENS` (4096), даже если платформа передала меньший `MAX_TOKENS`. При пустом или обрезанном ответе лимит удваивается до 8192. В конце прогона `solution.py` пишет в stderr сводку: сколько ответов от модели, сколько запасных, статусы, статистика вызовов LLM, первые ошибки.

`solution.py` укладывается в 20 минут: потоки по `MAX_WORKERS`, ретраи на 429/5xx; по среднему времени ответа прогнозирует итог и, если прогноз выше 80% бюджета, отключает самопроверку; `submission.csv` перезаписывается после каждого ответа; при сбое модели или тайм-ауте вопрос получает извлекающий ответ из найденных положений.

Локальный прогон в формате платформы:

```bash
mkdir -p /tmp/run/data && cp data/knowledge-base.zip /tmp/run/data/ && cp data/raw/demo_questions.csv /tmp/run/data/questions.csv
cd /tmp/run && LLM_BASE_URL=... LLM_API_KEY=... python /path/to/solution.py
```

## Тестирование

Все офлайн-проверки одной командой (ключ не нужен):

```bash
./tools/run_tests.sh
```

| Проверка | Что гарантирует |
|---|---|
| `tools/selftest.py` | 30 проверок ядра: санитизация, редакции, разбиение, диалоги, аудит ссылок (0 ложных срабатываний на эталонах) |
| `tools/retrieval_check.py` | нужная статья закона попадает в контекст (15/15) |
| `tools/edge_cases.py` | `solution.py` корректен при BOM/CRLF, лишних колонках, повторах id, пустом вопросе, `kb.zip`, вложенных папках, DOCX, cp1251, базе-папке, без `DATA_DIR` |
| `tools/chaos_test.py` | прокси отвечает 429/500, `<think>`, обрезанным JSON, пустым ответом, реранкер недоступен — сырой JSON в ответы не попадает |

Дополнительно проверено: образ собирается, контейнер healthy и работает не от root; сабмит запускается в чистом `python:3.12-slim` только с `requirements.txt` из ZIP; совместимость с Python 3.9+.

## Порядок проверки основного сценария

1. `docker compose up --build`, открыть http://localhost:8000 (в шапке — «21 документов · модель подключена»).
2. Нажать пример «Какая арендная плата по договору с ООО «Северный Склад»…» → ответ 450 000 ₽, до 5-го числа, ссылки на п. 3.1–3.2; справа подсвечены фрагменты, клик открывает договор.
3. «Договор на 12 млн рублей заключали в августе 2024…» → применена редакция регламента от 10.01.2023 (порог 10 млн), а не действующая.
4. «Подскажите гарантию по договору с «Альфой»» → уточняющий вопрос с двумя вариантами.
5. «Какой размер пособия по беременности и родам?» → обоснованный отказ: таких документов в базе нет.

## Известные ограничения

- Законы в базе только в действующей редакции; исторические редакции законов ассистент не восстанавливает.
- Документы компании кладутся в контекст целиком, пока их суммарный объём ≤ `COMPANY_FULL_CHARS` (60 000 символов); при росте базы включается поиск по ним.
- Качество зависит от модели, заданной платформой (DeepSeek V4.1 Flash); стиль ответов настроен на краткость (до ~150 слов).
- Персональные данные в базе — вымышленные.
